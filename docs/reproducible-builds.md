# Reproducible npm builds

VibraHeal uses a committed npm lockfile so CI and local clean installs resolve the same dependency graph.

## Source of truth

- `package.json` declares the dependency ranges the project accepts.
- `package-lock.json` records the exact resolved graph, registry locations, and integrity hashes used for reproducible installs.
- The lockfile is generated by npm. Do not hand-edit it.

The initial lockfile was generated on the reproducible-builds branch with Node 22 after Sound Lab Revival Phase 2 was merged.

## CI contract

GitHub Actions remains read-only and uses:

1. Node 22.
2. npm cache data keyed from `package-lock.json` through `actions/setup-node`.
3. `npm ci` for a clean install from the committed lockfile.
4. A clean-lock check with `git diff --exit-code -- package-lock.json`.
5. The existing automated test, TypeScript build, passive-guidance split, bundle-budget, vendor-separation, and production-manifest-history gates.

`npm ci` must fail rather than silently rewrite the dependency graph when `package.json` and `package-lock.json` disagree.

## Lockfile versus production history

The lockfile and the production-manifest-history baseline serve different purposes.

- `package-lock.json` is the current exact install graph for reproducible builds.
- `config/production-manifest-baseline.json` is a historical reviewed snapshot used to describe what has changed since that point.

Do not rewrite the historical manifest baseline merely to make its dependency-change count return to zero. A dependency difference in that report can be useful history while the current lockfile still guarantees a stable install graph.

The first locked CI run confirmed the existing historical difference already seen before this phase: `@react-three/drei` resolves to 10.7.8 while the older production-history snapshot records 10.7.7. The other tracked runtime dependency versions matched that historical snapshot.

## Updating dependencies

A deliberate dependency update should:

1. Change the intended dependency declaration when needed.
2. Run npm's normal dependency update/install command locally under the supported Node version.
3. Review both `package.json` and `package-lock.json` changes.
4. Commit the lockfile with the dependency change.
5. Run `npm ci`, tests, and the production build before merge.
6. Review the production manifest history for dependency and bundle changes.

Do not delete the lockfile to make a dependency conflict disappear. Resolve the intended dependency state and regenerate the lock deliberately.

## What this does not change

This infrastructure phase does not change Sound Lab audio, saved sessions, Backup Format v2, the journal, Animal Calm, Nature Mixer, review-artifact formats, runtime storage behavior, privacy behavior, or medical/wellness claims.

A locked dependency graph improves repeatability. It does not prove that a dependency is bug-free, secure forever, or appropriate for every future release; dependency review and updates remain deliberate maintenance work.
